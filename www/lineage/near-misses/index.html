What the sources say 75

  1. Ka-Ping Yee, PEP author PEP 3134, Exception Chaining and Embedded Tracebacks, Rationale 12 May 2005; Final in Python 3.0 source ↗

    As for other languages, Java and Ruby both discard the original exception when another exception occurs in a catch/rescue or finally/ensure clause. Perl 5 lacks built-in structured exception handling. For Perl 6, RFC number 88 proposes an exception mechanism that implicitly retains chained exceptions in an array named @@. In that RFC, the most recently raised exception is exposed for matching, as in this PEP; also, arbitrary expressions (possibly involving @@) can be evaluated for exception matching.

    The next paragraph turns to C#, whose InnerException property is set explicitly through exception constructors rather than by the runtime.

  2. Ka-Ping Yee, author of PEP 344 python-dev mailing list 20 May 2005 source ↗

    Describing his research into implicit exception chaining, Yee tells python-dev that Perl 6's proposed @@ was the sole precedent he managed to find.

  3. Collin Winter, PEP author; rejection notice by Guido van Rossum PEP 3133, Introducing Roles 1 May 2007; Rejected source ↗

    This system was originally called "traits" and implemented for Squeak Smalltalk. It has since been adapted for use in Perl 6 where it is called "roles", and it is primarily from there that the concept is now being interpreted for Python 3. Python 3 will preserve the name "roles".

    Guido van Rossum's rejection notice, at the top of the PEP, says it pushed PEP 3119, the abstract base classes Python adopted instead, toward a simpler design, and that he prefers that PEP as it now stands. The PEP's examples are adapted from Curtis Poe's article on Perl 6 roles.

  4. Guido van Rossum, Python's creator python-3000 mailing list, PEP 3133 discussion, message 007666 15 May 2007 source ↗

    Guido says that even if roles had equal standing he would still choose ABCs, since an ABC can serve as a base class and supply implemented methods, and questions what roles would contribute beyond them.

  5. Guido van Rossum, Python's creator python-3000 mailing list, Accepting PEP 3119, rejecting PEP 3133, message 007913 24 May 2007 source ↗

    Guido announces his decision on the two competing proposals: PEP 3119's abstract base classes are accepted and PEP 3133's roles are rejected.

  6. Stefan Marr, RFC author PHP RFC: Traits for PHP, version 1.5 6 Mar 2008 source ↗

What other languages valued

When another community cites Raku approvingly, it is usually for a small, cleanly reasoned detail, often in a survey of how languages handle it. The details cited are string increment, start-exclusive ranges, default rationals, Rat literals, grapheme-level dot, /x by default, assuming, Range matching, chained comparison, dual-precedence and/&&, Whatever placeholders and uncoloured functions.

Proposals from core-team members

Core-team members argued from Perl 6 more often than the proposal archives show. Two of their proposals were withdrawn within days, for reasons of consistency and tooling rather than anything about Perl 6:

  • Patrick Walton's -> closures for Rust (2012);
  • Brad Fitzpatrick's ... statement for Go (2019).

Python came closest

  • PEP 3133 shows that Python's designers read Perl 6 during the Python 3000 period. Guido van Rossum used it mainly to push PEP 3119 toward a more minimal design (PEP 31333).
  • PEP 3134 is as close as Python comes to Perl 6 lineage in a shipped feature. Its wording places RFC 88 beside Java, Ruby and C# as prior art (PEP 34476).
  • Its author's own python-dev message names Perl 6's @@ as the only precedent he found. That comes very close to a borrowing (python-dev2).
What the sources say 1

  1. Ka-Ping Yee, PEP author PEP 344, Exception Chaining and Embedded Tracebacks, Rationale 12 May 2005; superseded by PEP 3134 source ↗

    As for other languages, Java and Ruby both discard the original exception when another exception occurs in a catch/rescue or finally/ensure clause. Perl 5 lacks built-in structured exception handling. For Perl 6, RFC number 88 proposes an exception mechanism that implicitly retains chained exceptions in an array named @@. In that RFC, the most recently raised exception is exposed for matching, as in this PEP; also, arbitrary expressions (possibly involving @@) can be evaluated for exception matching.

    PEP 3134, which superseded this PEP, keeps the paragraph as it is; the next one turns to C#'s InnerException.
