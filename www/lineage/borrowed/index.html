  1. Becca (then Brent) Royal-Gordon, later an SE-0168 co-author swift-evolution mailing list, thread "multi-line string literals.", message 015738 25 Apr 2016 source ↗

    Recalls that Perl 6's redesign took a heredoc's base indentation from the indentation of its delimiter, and asks whether Swift should treat multi-line literals the same way.

  2. John Holdsworth, later SE-0168's lead author swift-evolution mailing list, thread "multi-line string literals.", message 016646 5 May 2016 source ↗

    Proposes that the lexer strip each line's margin by the whitespace that precedes the closing quote, explicitly as Perl 6 does.

  3. John Holdsworth, Becca Royal-Gordon and Tyler Cloutier, authors; Joe Groff, review manager Swift Evolution proposal SE-0168, Multi-Line String Literals Apr 2017; implemented in Swift 4.0 source ↗

    Specifies triple-quoted multi-line strings whose lines all lose the indentation found ahead of the closing delimiter; the text never mentions Perl or Perl 6.

  4. Joe Groff, review manager, for the Swift core team Swift Forums, SE-0168 acceptance announcement 19 Apr 2017 source ↗

    Accepts the proposal with revisions: where the closing delimiter sits fixes the indentation for the whole literal, and under-indented or inconsistently indented lines are errors. Perl goes unmentioned.

  5. Yukihiro Matsumoto (Matz), Ruby's creator Matz's diary on rubyist.net, entry on the new lambda grammar (Japanese) 22 Jul 2005 source ↗

    Answering Evan Phoenix, Matz confirms Perl 6 has the arrow syntax and is its source, and says he once tried an arrow block form for method calls but dropped it as too radical.

  9. George Peter Banyard, the RFC's author PHP RFC: Path to Saner Increment/Decrement operators 21 Nov 2022; voted 25–0, 28 Jun–12 Jul 2023 source ↗

  10. Michael Ilseman, Apple engineer leading Swift's String and standard-library work GitHub gist "State of String: ABI, Performance, Ergonomics, and You!" 10 Jan 2018 source ↗

  11. Michael Ilseman, lead designer of Swift's string processing Swift Forums, "Declarative String Processing Overview", post #46 1 Oct 2021 source ↗

Swift's multi-line strings are the one case in which a Perl 6 design decision shipped whole in a major language outside the Perl family. On 25 April 2016, in the swift-evolution thread on multi-line string literals, Becca Royal-Gordon (then posting as Brent, and earlier a perl6-language participant and Parrot pumpking) described Perl 6's choice to take a heredoc's base indentation from its delimiter and asked whether Swift should do the same; on 5 May John Holdsworth replied that the lexer could strip the margin by the whitespace before the closing quote "as per Perl6" (0157381; 0166462; forum #2115). Both became SE-0168's authors, with Tyler Cloutier. The proposal specifies that whitespace in front of the closing delimiter is removed from every line and never mentions Perl 6; in the April 2017 review Royal-Gordon summed up Perl 6's heredocs as Perl 5's plus de-indenting, and on 19 April Joe Groff accepted the proposal with the rule that the closing delimiter's position sets the indentation of the whole literal, making under-indentation an error where Raku only warns (SE-01683; review #1716; Accepted4). The credit lives where Swift regex's does, in the discussion rather than the proposal, but unlike the regex work the rule itself reached Swift 4.0 unchanged.

Ruby's arrow is the best-documented case and sets the pattern for the rest. The record is contemporaneous: Matz's diary listed a Perl6-style anonymous function among candidate lambda syntaxes on 1 July 2005 and on 22 July said the -> proposal came from Perl 6, weighing Perl 6's cultural closeness to Ruby against doubt over when, or whether, Perl 6 would be used (diary 1 Jul17; diary 22 Jul5). He committed it as new and very experimental on 27 July 2005 — five months after Pugs made pointy blocks runnable and three and a half years after A4 specified them — and two days later told ruby-dev that the grammar was aligned with Perl 6, in a comparison table that set Perl6/Ruby2 -> (x,y) {...} beside Groovy's and Haskell's forms (ruby-dev:266507). In May 2008, asked on ruby-core whether Perl 6 has the -> syntax, he answered "Yes. It's the origin." Evan Phoenix had asked after quoting Matz's earlier remark that a syntax Ruby shared with Perl 6 would gain mind-share quickly; in reply Matz also noted that Perl 6 goes further, with for obj -> var { }, and that a method(arg) -> x { } block form he had tried himself was dropped (ruby-core:1673318; ruby-core:167348; ruby-core:1676619). What crossed was only the token: Ruby's ->(x) { } builds a lambda object, whereas Raku's -> introduces a Block with a signature that for, given and with consume. PHP's increment RFC by George Peter Banyard is the only shipped mainstream feature whose design text says it follows Raku, and its framing is a survey: it treats Raku as a Perl successor whose string increment gives consistent results where PHP's does not (PHP RFC9). A 2013 internals thread on letter decrementing had already cited S03's decrement, which does not fully mirror increment, and changed nothing (6818420).

Swift's regex work is the deepest engagement and the clearest case of attrition between design and ship. The interest started in the core team: Chris Lattner urged forum readers to study Perl 6's regexes from December 2015, wrote in January 2017 that Swift could learn a lot from Perl 6's grammars, and was still praising them in March 2020, while Joe Groff and Dave Abrahams pointed to Perl 6's approach and its recursive grammars in the same January 2017 thread (335/421; 876/922; 4939/13023; 34373/1024; 4939/6825; 4939/15326). Michael Ilseman's January 2018 "State of String" gist set Swift the goal of beating Perl at string processing, cited Apocalypse 5 as Perl's clean-up of its own regex mess, noted that Perl 6 has a PEG-like grammar system, and listed Perl 6 features Swift should take outright: whitespace-insignificant syntax, named captures, multi-line matching and regex interpolation. It also proposed ratcheting, frugal quantifiers and Raku's % separator quantifier, and asked whether alternation should use longest-token matching (gist10). By October 2021 Ilseman was explaining the retreat: familiarity with traditional syntax was decisive for a literal, so the team would spend its appetite for novelty on a separate Pattern type, even though he personally preferred Raku's syntax (forum #4611). In Hamish Knight's March 2022 regex-syntax pitch, Joe Groff's first reply again cited Raku for making /x the default (Swift Forums27), and SE-0354 split the difference, making extended syntax mandatory in multi-line #/…/# literals while rejecting non-semantic whitespace for single-line ones (SE-035428). A5's 2002 choices thus reached Swift 5.7 two decades later in altered form — composable, named sub-patterns in RegexBuilder (SE-035129), PEG-style ordered choice credited to PEGs (SE-035030), and mandatory extended syntax in multi-line literals — while the attribution survives only in a gist and forum posts. SE-0363 even defines a [raku] reference link that its body never uses (SE-036331). Joose is a genuine Perl 6 → other-language transmission, but it passed entirely through Moose and remained niche (Joose manual14).

  4. Chris Lattner, Swift's creator, core team Swift Forums, "Regular expressions in Swift", post #10 15 Mar 2020 source ↗

    Lattner says Perl 6 has excellent ideas for regex support after long community thought, and that although the language is not widely used, Swift should study and learn from its strengths.

  5. Joe Groff, Swift core team Swift Forums (swift-evolution import), "Strings in Swift 4", post #68 23 Jan 2017 source ↗

    Groff warns against a narrow focus on regexes, says the Perl 6 designers grew regex support into arbitrary grammars, and recommends Swift begin from that level by examining their work.

  6. Dave Abrahams, Swift core team Swift Forums (swift-evolution import), "Strings in Swift 4", post #153 26 Jan 2017 source ↗

    Abrahams explains that regexes cannot parse languages like Swift and that he has in mind parsers of the kind Perl 6's recursive grammars allow, linking examples.

  7. Joe Groff, Swift team, replying to Hamish Knight's pitch Swift Forums, Regex Syntax pitch thread, post #2 (the pitch itself is Hamish Knight's) 3 Mar 2022 source ↗

    Groff backs a PCRE baseline, singles out free-whitespace /x mode as the most valuable tweak, and notes that Raku made it the default for pattern literals, urging new languages to do likewise.

  8. Hamish Knight, Michael Ilseman and David Ewing, authors Swift Evolution proposal SE-0354, Regex Literals 2022; implemented in Swift 5.7 source ↗

    Enables extended (?x) syntax, with non-semantic whitespace and comments, in multi-line #/…/# literals, and rejects that default for single-line ones for familiarity and compatibility; it cites Perl, never Raku.

  9. Richard Wei, Michael Ilseman, Nate Cook and Alejandro Alonso, authors Swift Evolution proposal SE-0351, Regex builder DSL 2022; implemented in Swift 5.7 source ↗

    Introduces RegexBuilder, a result-builder DSL for assembling regexes from reusable components, including other regexes and custom patterns, without mentioning Perl or Raku.

  10. Michael Ilseman, author Swift Evolution proposal SE-0350, Regex Type and Overview 2022; implemented in Swift 5.7 source ↗

    Calls Parsing Expression Grammars the nearest formal analogue of Swift's regex design, which uses ordered-choice alternation, possessive quantification and recursive subpattern calls; it never mentions Perl or Raku.

  11. Nate Cook and Alejandro Alonso, authors Swift Evolution proposal SE-0363, Unicode for String Processing 2022; implemented in Swift 5.7 source ↗

    Compares Swift's grapheme-cluster regex matching with NSString, Java, Ruby and Perl, and lists a reference link to Raku's regex documentation that nothing in the proposal's text uses.

Two further transmissions sit below the language level, and neither counts as a language borrowing. Matthew Barnett, author of the third-party Python regex module, wrote in 2008 that his variable-length lookbehind, done by matching backwards, came from a page on how Perl 6 could implement it; he names no page, but S05 had described after as reversing the syntax tree since at least April 2006, and CPython never took the module into re (cpython#4807532; S0533; PyPI regex34). And the Rust Grammar Working Group's notation took Raku's % and %% separator modifiers, which eddyb, then on Rust's language and compiler teams, attributed to Perl 6 in 2018; the wg-grammar files use %% throughout, while the Rust Reference keeps its own notation (internals #835; expr.lyg36).
